Anexure

A1. No-change commitment for v2.0 body

This Anexure is strictly additive. All existing architecture content remains unchanged.

A2. Approval ID operational semantics (additive)

Existing v2.0 text requires approval ID for outbound send. This annexure adds implementation guidance:

  • Treat approval ID as single-use and expiring.
  • Bind it to workspace, task/issue, channel/thread, recipients and approved final text.
  • If text changes after approval, require a new approval ID.
  • Consume approval ID atomically with send-attempt logging.

A3. Idempotency keys (additive)

To avoid duplicate tasking or duplicate sends under retries:

  • Inbound email dedupe key: workspace + provider message id.
  • Task creation dedupe key: workspace + inbound message id.
  • Approval request dedupe key: issue + draft hash + category.
  • Decision callback dedupe key: approval request + callback nonce/event id.
  • Send dedupe key: approval id + channel.
  • Ledger sync watermark per workspace/provider stream.

A4. Reconciliation workers (additive)

  • ORBIT ↔ Paperclip state reconciliation (tasks, approvals, done/blocked outcomes).
  • Provider delivery reconciliation for uncertain send outcomes.
  • Rules render/version reconciliation (database approved rules vs rendered profile context).

Irreconcilable drift should raise an operator incident and remain auditable.

A5. MCP catalog architecture clarification (additive)

v2.0 already references official hosted MCP usage and policy gateway. This annexure makes explicit:

  • ORBIT maintains a curated MCP catalog for supported integrations.
  • Per-instance connection activation is from approved catalog entries in MVP.
  • Tool visibility is role/profile scoped and least-privilege.
  • Write-capable MCP access requires policy approval and audit.
  • Front Desk remains deterministic and must not bypass approval path via MCP additions.

A6. Adapter consistency clarification

Where v2.0 contains both gateway-centric design and local-adapter examples, production customer instances should follow the gateway-centric design as the operational standard.

A7. Canonical truth mapping (additive)

  • ORBIT Postgres: approvals, authority decisions, receipts, customer-visible audit truth.
  • Paperclip: runtime orchestration state.
  • Hermes profile state: working memory/session runtime state.
  • Outbound evidence: provider delivery metadata + ORBIT receipt event.

A8. Annexure status

This Anexure adds implementation clarity only. It does not supersede ADRs or any existing v2.0 section text.
