
## Anexure

### A1. Vision precision: trust at the action boundary
The existing vision remains unchanged. This annexure clarifies an operational interpretation:
- ORBIT trust is not only “approval exists,” but “approval is enforceable and replay-safe at send time.”
- This strengthens the same vision promise without changing product direction.

### A2. Extensibility strategy statement (MCP)
To preserve simplicity for SMBs:
- ORBIT should present integrations as curated capabilities, not raw infrastructure choices.
- A curated MCP catalog with role-scoped access supports “power with safety.”
- This aligns with the document’s depth-over-breadth principle.

### A3. “Unique” differentiation clarification
The primary moat remains the existing combination already present in this vision:
- dedicated instance per customer,
- authority-aware approvals,
- deterministic Front Desk lane,
- receipts + cost + learning loop,
- managed setup.
Integrations support this moat; they are not a replacement for it.

### A4. Reliability as trust (implementation lens)
This annexure recommends explicitly treating:
- idempotency,
- reconciliation,
as part of product trust, not only engineering quality.
Reason: SMB trust is broken most by visible duplicate/wrong sends, not by internal architecture terms.

### A5. Product-language continuity
No change to existing language principle:
- customers should continue to see teammate/outcome language only.
- internal terms (engine/adapter/token) remain internal to docs and implementation surfaces.

### A6. Annexure status
This Anexure is additive to v2.0 and does not modify any approved vision statement in the main body.
